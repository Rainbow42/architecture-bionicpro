# BionicPRO

## Вход и границы страны

Я оставила управление протезом на чипе: сетевой вход и отчётность не должны попадать в контур реакции на миосигнал. Приложение донастройки по-прежнему взаимодействует с чипом, API принимает телеметрию, а ML-инженер работает через свой CLI. Интернет-магазин и CRM сохраняют существующую связь.

Для каждой страны нужен отдельный контур: локальный Keycloak, каталог пользователей, CRM, телеметрия, ClickHouse, S3 и кеш отчётов. Выбор страны происходит до входа. Учётная запись имеет составной идентификатор `(issuer, sub)`, а не общий email. Один и тот же email у разных IdP не означает одного человека; автоматическое связывание аккаунтов по email выключено.

Федерация LDAP работает внутри страны представительства. В стенде каталог эмулируется отдельным OpenLDAP-контейнером, а роли `user` и `prothetic_user` сопоставляются с realm roles. Для реального развёртывания соединение с каталогом нужно защищать LDAPS с проверкой сертификата. Копировать зарубежный каталог в российский realm нельзя: даже федерация с импортом профиля переносит персональные данные. Импорт допустим только между локальным каталогом и локальным Keycloak той же страны.

Внешний IdP подключается к региональному Keycloak через Identity Brokering. Яндекс ID предусмотрен для российского контура. Профиль, токены, OTP-секреты, резервные копии и журналы с идентификаторами остаются в выбранной стране. Глобальный слой может содержать публичный каталог региональных адресов, но не медицинские данные и не пользовательские сессии. До выхода в конкретную страну нужно отдельно подтвердить требования к размещению и основания передачи данных; схема не заменяет такую проверку.

## Сессия

Браузер переходит на `/auth/login`. `bionicpro-auth` создаёт одноразовые state, nonce и PKCE verifier, сохраняет их на сервере и отправляет в Keycloak только S256 challenge. Callback проверяет привязку попытки входа к HTTP-only cookie, state, подпись ID token, issuer, audience и nonce. Код обменивается на токены сервером.

Access token живёт 120 секунд. Refresh token хранится в памяти в зашифрованном виде, ключ приходит из локальной конфигурации. Сессия живёт час, имеет абсолютный срок и не продлевается ротацией. Каждый успешный запрос к защищённому ресурсу заменяет идентификатор сессии; старый сразу перестаёт работать. Фронтенд выполняет запросы последовательно. Параллельные вкладки могут потребовать повторного входа — в этой реализации нет окна, в котором старый идентификатор остаётся действительным.

Cookie имеет `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` и префикс `__Host-`. POST дополнительно проверяет Origin и CSRF-токен. Access/refresh tokens не попадают в JSON, localStorage, frontend bundle или URL скачивания. При истечении access token сервер сам использует refresh token, проверяет новую подпись и субъект. Ошибка обновления отзывает сессию.

В локальном стенде один процесс auth с хранилищем в памяти; перезапуск требует входа заново. Для нескольких реплик нужно вынести сессии в региональный Redis, шифровать refresh token и атомарно выполнять проверку и ротацию. Простое добавление нескольких workers здесь неправильно.

Вход по паролю и вход через брокер требуют OTP. Первый вход включает настройку TOTP. Password grant и implicit flow выключены. Сессионный вход Keycloak использует уже подтверждённую MFA-сессию; брокер дополнительно проходит обязательный OTP flow.

После входа через Яндекс ID интерфейс просит согласие на сохранение ограниченного набора полей профиля. Только после подтверждения сервер запрашивает профиль у Яндекса и записывает его в `profiles`. Самому Keycloak минимальный профиль нужен раньше для аутентификации; это не скрывается от пользователя. При отказе можно выйти без записи прикладного профиля.

## Отчёты и кеш

Начальный вариант задания 2: Airflow раз в пять минут читает CRM и телеметрию, группирует данные по владельцу, протезу и дню и записывает отдельную версию `reports_batch`. API читает готовые строки, не соединяет CRM и телеметрию во время пользовательского запроса.

Итоговый вариант задания 4: Debezium выполняет начальный snapshot CRM, затем читает WAL PostgreSQL. Kafka хранит события, Kafka Engine принимает их в ClickHouse, первая Materialized View переносит изменения в `crm_cdc`. Версия PostgreSQL LSN и ReplacingMergeTree обеспечивают идемпотентное применение повторов; удаление хранится как tombstone. Вторая, refreshable Materialized View, соединяет актуальную CRM (`FINAL`, без удалённых строк) с телеметрией и сохраняет новую версию `reports_cdc`.

Я выбрала refreshable view, потому что обычная incremental view с JOIN не пересчитала бы старые строки телеметрии после изменения CRM. Airflow запускает refresh и ждёт завершения, затем публикует в S3 маленький манифест завершённой версии. Если обработка падает, указатель остаётся на предыдущей успешной версии. API по умолчанию использует CDC-витрину. Режим `PIPELINE_MODE=batch` нужен для воспроизведения промежуточного решения второго задания; одновременно оба режима публиковать нельзя.

Даты API — полуинтервал `[start, end)` в UTC. Текущий незавершённый день не выдаётся. Если период выходит за опубликованный диапазон, ответ — 409 с доступными границами; пустой отчёт не подменяет ещё не обработанные данные. В учебном наборе телеметрия ограничена семью днями. В рабочей системе вместо полного чтения нужен источник с устойчивым watermark и политикой обработки опоздавших событий.

Владелец определяется только из подписанного токена, роль — `prothetic_user`. Пользователь не передаёт `user_id`. Администратор не получает неявного доступа к медицинским отчётам.

Путь объекта: `sha256(issuer + sub)/reports_cdc-<generation>/<start>_<end>.json`. Сначала API читает манифест и проверяет S3. При попадании ClickHouse не запрашивается. При промахе отчёт формируется один раз, сохраняется в приватный bucket, затем возвращается ссылка `/cdn/...`. Новая версия данных имеет другой URL, поэтому не требует очистки всего CDN. Старые версии нужны только на ограниченный срок: для промышленного запуска потребуется согласованная политика хранения в S3, ClickHouse и резервных копиях.

Nginx эмулирует CDN через reverse proxy с кешированием. Перед каждым запросом, включая HIT, `auth_request` проверяет сессию, роль и принадлежность пути. Bucket и origin API не доступны с хоста. Внешний ответ помечается `private, no-store`: личный отчёт не должен попасть в общий браузерный прокси-кеш. Внутренний кеш Nginx ограничен объёмом и временем. Ключ origin нужен только между Nginx и API и не приходит от браузера.

## Границы учебного стенда

Все данные синтетические. HTTP разрешён только на loopback `localhost:8088`; современные браузеры делают для localhost исключение при работе с Secure cookies. Для внешнего адреса обязателен HTTPS, корректный issuer/redirect URI и доверенные сертификаты. Такой стенд нельзя публиковать в интернете без настройки TLS, разграничения учётных записей БД, квот, резервирования и наблюдаемости.

У CDC есть задержка: работающий connector ещё не доказывает нулевой lag. Отчёт обозначает версию снимка, а не обещает мгновенно включать все изменения CRM. Перед промышленным запуском нужны мониторинг lag и replication slot, лимиты WAL, DLQ, контроль snapshot и проверка восстановления из backup.
